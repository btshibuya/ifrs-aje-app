# IFRS AJEアプリ　DB設計案 v0.1（プロトタイプ用）

- 対象：Supabase（PostgreSQL）無料プラン
- ファイル
  - `schema.sql`：テーブル・ビュー・ロック・変更履歴・アクセス制御
  - `seed.sql`：15論点と仕訳区分（30区分）の初期データ
- 検証：ローカルの PostgreSQL 16 で作成と動作試験を実施済み（Supabase の auth・storage は簡易な代替で試験）

## 1. 全体像

```
[マスタ]   会社 ─ 決算期（前期とつなぐ）
           論点 ─ 仕訳区分（累積／洗替／組換）
           グループ統一科目 ─ 科目マッピング（会社ごと）
           列マッピング・区分マッピング・会計方針（グループ共通＋会社ごとの上書き）

[取込]     元資料（原本・ハッシュ値） ─ 明細（チェック状況） ─ PDF項目の確認・手修正記録

[計算]     計算の実行（前提値のスナップショット）
             ├ 計算シートの行（計算式・値・元の明細）
             ├ 明細ごとの期末残高（翌期の起点）
             └ 仕訳 ─ 仕訳明細（計算シートの行に紐づく）

[管理]     進捗・確定ロック（会社×期×論点） ／ 変更履歴（自動記録） ／ BTrex開始仕訳の取込
```

## 3. 主な仕組み

### 方式ごとの出力
`journal_categories.carry_method` で決まります。
- **累積（cumulative）**：アプリは当期の変動分だけを出力する。期首残高はBTrexの開始仕訳で入る
- **洗替（reversing）**：アプリは当期末時点の全額を出力する
- **組換（reclass）**：アプリは当期の全額を出力する。翌期への引継ぎはない

税効果は内容ごとに区分を分けています（例：有給休暇引当金 → 有給休暇引当金（税効果）、方式も同じ洗替）。

### ロールフォワード
- 累積の論点は、前期の確定した計算の `item_balances` を起点に、当期の変動を加えて計算する
- 見積りの変更（耐用年数・割引率など）は、遡らず当期以降に反映する
- 前期末にあったのに当期の計算に出てこない明細は、`v_missing_carryforward` で検出する（除却・売却の処理漏れの防止）

### 確定ロック
- `work_status` を `locked` にすると、その会社×期×論点の明細・計算・仕訳を変更できなくなる（DB側で拒否）
- 変更するには、確定を解除する必要がある。解除の操作も変更履歴に残る

### 変更履歴
主なテーブルへの追加・変更・削除を、ログインユーザーとともに自動で記録します。履歴は読み取り専用です。

### ブラックボックスにしない仕組み
仕訳明細 → 計算シートの行（計算式・値） → 明細（取込ファイルの行・PDFのページ） → 元資料（原本・ハッシュ値）の順に、どの数字からでも遡れます。

## 4. 画面用のビュー

| ビュー | 画面 | 内容 |
|---|---|---|
| v_policy_matrix | 会社別方針一覧 | 会社×期×論点の有効な方針。会社ごとの上書きがあれば `is_company_override` が真 |
| v_impact_summary | 論点別影響額一覧 | 会社×期×論点×BS/PL/OCIの影響額（借方プラス） |
| v_progress | 進捗一覧 | 会社×期×論点の進捗（未登録は「未着手」） |
| v_unbalanced_entries | 出力前チェック | 貸借が一致しない仕訳 |
| v_missing_carryforward | 期首チェック | 前期末にあって当期に引き継がれていない明細 |

## 5. ログインとアクセス制御
- ログインは Supabase Auth（メールアドレスとパスワード）を使う
- 3名分のアカウントを招待で作成し、Supabaseの設定で新規登録を無効にする
- ログインした担当者は全データを読み書きできる（承認機能なしの前提）
- 元資料は非公開の保存領域（`source-files`）に置く

## 6. 動作試験の結果
| 試験 | 結果 |
|---|---|
| 確定ロック後の仕訳変更・削除 | 拒否された |
| 同じ論点・期で有効な計算を2つ作る | 拒否された |
| 方針一覧：グループ共通の税率と、会社ごとの上書き税率 | 期ごとに正しく切り替わった |
| 影響額一覧 | BS・PL別に正しく集計された |
| 引継ぎ漏れ：前期に2名、当期に1名の有給明細 | 消えた1名が検出された |
| 変更履歴 | 変更者つきで記録された |

## 7. 今後の課題

- **BTrexの出力レイアウト**：最終段階で `btrex_category_code`・`btrex_account_code` を使って対応する
- **本番化するとき**：権限の細分化、バックアップ、Microsoft 365でのログインなどを検討する
